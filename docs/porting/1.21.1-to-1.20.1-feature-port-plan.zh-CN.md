# 1.21.1 到 1.20.1 功能移植方案

## 目标

将 1.21.1 分支 2026-08-04 之后传送带相关改动，按功能单位移植到 1.20.1 分支。移植目标是行为和兼容性一致，不机械复制 commit、NeoForge API、1.21 数据组件或 1.21 专用构建脚本。

本方案只移植运行时功能；文档、`quickPlaySmoke`、1.21 专用 Gradle 配置和纯版本范围变更不作为功能移植内容。

## 基线与约束

- 目标分支：`1.20.1`，当前工作分支为 `codex/port-1.20.1-belt-features`。
- 目标环境：Minecraft 1.20.1、Forge 47.1.33、Create 6.0.8-291、Java 17。
- 参考环境：Minecraft 1.21.1、NeoForge 21.1.219、Create 6.0.10-281、Java 21。
- 第三方行为优先查阅 `ref/1.20.1/` 和 `ref/1.21.1/`，依据 `ref/SOURCES.md` 判断版本 caveat。
- Forge 能力系统使用 `LazyOptional` / `net.minecraftforge.items.IItemHandler`；不能直接复制 NeoForge `Capabilities`、`RegisterCapabilitiesEvent`、`net.neoforged.neoforge.items.IItemHandler`。
- 1.20 的 Mixin 目标按本地 Create 1.20.1 参考和编译结果确认；涉及 Minecraft 映射的目标不机械添加 `remap = false`。
- 每个阶段完成后先做最小验证，再提交；Mixin 阶段额外执行可行的客户端启动检查。

## 功能分组与执行顺序

### 阶段 0：基线与方案

提交本文件，记录目标、依赖、阶段、验证和已知不适用项。之后所有实现按照本文件执行。

### 阶段 1：低风险行为与生命周期修复

先移植不依赖大型架构重构的功能：

1. 漏斗红石暂停恢复：`fb322551`，在漏斗自定义模式判断前尊重 `POWERED`。
2. 隧道岩浆带 casing 自动设置：`988b8663` 中仅移植 `BeltTunnelItemMixin` 及 mixin 配置项。
3. 史莱姆带、动力带链式破坏渲染属性：`b0daef42`。
4. 史莱姆带库存一致性：`fa8264d2`，包括插入前刷新方向、写 NBT 前 flush pending 状态。
5. 史莱姆带捕获轨道选择修复：`0b331974`。
6. 链条初始化失败退避重试：`ec97d409`。
7. 传送带清空：`26d36a35`，使用 1.20 可用的 `Clearable` / `clearContent` 语义。

阶段提交：`port(1.20): migrate belt correctness fixes`。

### 阶段 2：8 月 4 日生命周期前置基线与能力缓存

由于 `f6143316` 在 8 月 5 日合并时携带了 8 月 4 日晚间的基础改动，将以下功能作为后续链条和交互的前置：

1. `TransformableBlock` 与 `CBBeltTransform`：史莱姆带、动力带支持结构运动中的轴向变换。
2. 史莱姆带 `clearKineticInformation()` 保留乘客：`2771ee1a`。
3. 使用缓存方块状态：`0c7a7c4e`。
4. 史莱姆带 `surfaceFor` / `Track.values()` 优化：`30a490d5`。
5. 链条重连时失效隧道和物品能力缓存：`2108bdb9`。按 Forge 的 `LazyOptional` 和能力失效语义重写。

阶段提交：`port(1.20): migrate belt lifecycle baseline`。

### 阶段 3：标准物品传送带交互

以 `a6ea0078` 为功能来源，移植“标准物品表面”协议，而不是直接搬运文件：

1. 新增 `StandardItemBeltBlock`、`StandardItemBeltPort`、`StandardItemBeltPortResolver`。
2. 让岩浆带和史莱姆带实现共同的方块/方块实体接口；史莱姆带只暴露前轨道。
3. 抽取公共机械臂交互，合并原史莱姆带机械臂逻辑，并应用于岩浆带。
4. 抽取公共粉碎轮交互和 tick context，替换两套重复 handler。
5. 将漏斗、盆地、黄铜隧道、隧道能力和 Create capability 注册从史莱姆专用判断改为通用 port 判断。
6. 合并 `BeltTunnelCapabilityInvalidator`，确保重连/移除/卸载时不加载区块且清理 Forge 能力缓存。
7. 同步 `a42d3ec3` 的机械臂方块 registry 延迟解析修复；不得把 1.21 registry supplier 写法直接复制成 1.20 不兼容形式。

阶段提交：`port(1.20): unify standard item belt integrations`。

### 阶段 4：完整史莱姆带 Create 交互覆盖

以 `b66a5877`、`46f4be57` 为来源，检查阶段 3 后是否仍有史莱姆专用分支，补齐：

- 史莱姆带隧道输入/输出和前轨道方向判断；
- 盆地输出、漏斗插入和停止状态判断；
- 机械臂抓取/放置；
- 粉碎轮交接；
- Mixin 中对普通 Create belt 与两种生物科技 belt 的优先级和回退行为。

该阶段与阶段 3 可能在实现上交叠；若阶段 3 已完整覆盖，则只提交剩余行为修复，不重复重构。

阶段提交：`port(1.20): complete belt create integrations`。

### 阶段 5：通用链条拓扑与结构运动兼容

以 `d99e5e18`、`dc9af97f` 为来源，移植：

1. `CBBeltChain` / `CBBeltChainBlock` 的统一链条遍历、最大长度和未加载区块安全处理。
2. 岩浆带、史莱姆带、动力带统一实现链条段接口。
3. 链条初始化、重连、移除、`nextSegmentPosition` 和 controller 解析统一化。
4. Create contraption 对所有生物科技传送带的识别。
5. Sable/Simulated compat 只在 1.20 API 和依赖存在时适配；不存在的可选 API 保留安全 no-op，不引入 1.21 依赖。

阶段提交：`port(1.20): unify belt chain topology`。

### 阶段 6：蓝图链条原子放置

以 `94ed4dc6` 为来源，移植 `CBBeltChainPlacement`、placement segment/block 和相关 schematic/deployer/launched-item 逻辑：

- 链条放置期间先收集和验证完整快照；
- 完整链条成功后原子提交，失败时不留下半条链；
- 保留 pulley、casing 等链段元数据；
- 按 1.20 Forge 的 `BlockSnapshot`、NBT 和 Create schematic API 调整签名。

阶段提交：`port(1.20): place belt chains atomically`。

### 阶段 7：渲染与几何结构优化

在功能和链条行为稳定后再移植结构性优化：

1. `fcbad17d`：统一 buffered/Flywheel belt visual、render state 和 client registration，按 Flywheel 1.0.5 API 改写。
2. `d60d9d09`：共享稳定链段操作、connector geometry、selection、shape set 和 slicer。
3. `d5b3955e`、`aa52310f` 中与渲染/visual 有关的部分选择性移植；1.20 保留 `ItemStack#getMaxStackSize()`，不复制 `DataComponents.MAX_STACK_SIZE`。
4. `a4af0c3e` 的具名方块事件常量作为低风险清理，在相关文件稳定后合并。

阶段提交：`port(1.20): align belt visuals and geometry`。

## 不移植内容

- 1.21 专用 `quickPlaySmoke`、`test.py` 构建参数、文档和 README 改动。
- `gradle.properties` 中 1.21 Create 版本范围和 NeoForge/Java 21 配置。
- Giant Frog 等 1.20 分支不存在的功能。
- 只改变版本元数据的提交。
- 不能在 1.20 找到对应 API 的 1.21 多方块 capability 注册方式；保留 1.20 现有代理方块实体，除非能以 Forge 语义等价实现。

## 验证策略

每阶段：

1. `git diff --check`。
2. `./gradlew compileJava`，必要时先 `--offline`，失败再报告依赖原因。
3. 检查生成的 `create_biotech.refmap.json`，尤其是改动过的 Mixin。
4. 功能相关的 Mixin 阶段执行最小客户端启动/已有 `quickPlayClient` 检查；非 Mixin 阶段不强制启动客户端。
5. 提交前记录实际验证结果和未解决 caveat。

## 提交纪律

- 每个阶段只提交该阶段相关文件。
- 不使用 merge commit 作为移植手段，不把 1.21 commit 整体 cherry-pick 到 1.20。
- 若某个大阶段在编译上被 Forge/Create API 阻塞，先保留已完成的小功能提交，并在本文件追加状态和阻塞原因，再继续可独立移植的阶段。
